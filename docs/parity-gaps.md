## ShareModal's silent failure — RESOLVED

Confirmed symptom, not a theoretical gap: a real bug report ("creatives uploaded via the live site don't display through a shared-review link") turned out to have nothing to do with upload, storage, or live vs. local — every asset checked (both a throwaway repro and the actual production data) had a real, downloadable Storage object exactly matching its DB row. The cause was `shared_link_allowed_creative_ids()`'s unconditional `stage >= 5` rule (supabase/seed.sql) silently excluding creatives still in the internal band (1–4) — which is *every* creative New Brief creates, since nothing anywhere in the app ever advances a creative's stage (confirmed: no stage-updating mutation exists in any hook, component, or page). ShareModal created the link successfully regardless and handed back a working URL, with no indication anything would be missing from it.

**Fixed**: `lib/shared-link-eligibility.ts` mirrors that RPC's rule client-side (unit-tested against all four scopes) and `ShareModal.tsx` previews it live as scope/picks change — before the link is created, not blocking it. Zero eligible creatives gets a plain `.note.warn` explaining they're still in Concept, Copy, Design or Internal QC; a partial exclusion gets a calmer count ("N of M won't show"). There are legitimate reasons to create a link ahead of the work being ready, so creation is never blocked, only informed.

Spec coverage: `tests/e2e/share-eligibility.spec.ts`, zero-eligible and partially-eligible cases. Fixed two more fixture-teardown gaps this surfaced along the way (same class as `format_directions` below): `shared_links` created through the real UI, not `frank.createSharedLink()`, weren't covered by the token-tracking cleanup, and `creatives` created via a new `createCreativeAtStage()` fixture helper needed the same. Both now sweep by `agency_id` like the other tables.

## Stage transitions — RESOLVED (minimal), rest still deferred

**Built**: `supabase/migrations/phase9_advance_creative_stage.sql` — staff can move a creative from the internal band (stage < 5) to Client Review, and back to Internal QC (stage 4). Nothing else; exception-setting, approval attribution and an audit table all stay deferred, exactly as scoped below. `advance_creative_stage(p_creative_id, p_direction)` is `SECURITY DEFINER`, `search_path` pinned to `public` (no `extensions` needed — no `crypt()`/pgcrypto call here, unlike the guest-path functions `phase7_fix_pgcrypto_search_path.sql` had to widen). Entry point is a button on the creative review page itself (`+ New Brief`'s sibling toolbar), gated on the same `isStaff` (real membership) pattern used everywhere else in this app.

Also resolved along the way: `creatives_update`'s RLS, previously broad enough that a client-role session could write *any* column on a creative it could read — narrowed to staff-only. The scoping below already flagged this as broader than anything the UI exposed; closing it was a precondition for building the transition at all, not a separate decision. A future client-permitted transition (approving, say) should get its own `SECURITY DEFINER` function rather than widening this policy back out — `advance_creative_stage` is the template.

Verified empirically against real authenticated sessions, both roles, before any UI was written: a client's direct table write on `stage` is silently blocked (0 rows, no error — ordinary RLS semantics); a client's call to `advance_creative_stage` is explicitly rejected (`not permitted`); staff's calls succeed and the legal-move guards hold (`already at or past Client Review` / `only a Client Review creative can move back to internal` on the wrong-direction case); staff's direct table write on `stage` still succeeds too, confirming `creatives_update` isn't locked to the RPC path, only to staff. Spec coverage: `tests/e2e/stage-transition.spec.ts` — a staff advance making a creative visible through a real shared link, a client having no entry point and being rejected at the RPC layer directly (not just UI absence), and ShareModal's eligibility warning (see above) clearing once the move happens.

The rest of this entry is the original scoping this was built against — still accurate for what's still deferred (exception, audit, approval attribution), against the prototype's intent and this schema's actual constraints:

**What the prototype intends** (`frank-prototype.html`): fewer real transitions than the UI suggests, and — tellingly — the prototype's own script doesn't fully implement all of them either.

- **Artwork lands on a brief with none** (`$("#upSend").onclick`): bumps stage to at least 3 (Design) — *not* straight to Client Review. Uploading isn't "ready for the client," just "past Concept/Copy."
- **"Save as Coming Soon"** (`$("#upDraft").onclick`): explicitly touches nothing — its own toast says "not visible to the client."
- **Approve** (`doApprove`, wired to `#approve`): gated on unresolved comments (confirms first if any exist); the button's own label switches between "Approve" (client mode) and "Approve on Behalf" (agency mode) — **both roles can approve**, staff's version is explicitly framed as recording an approval given some other way (phone, email), not a separate staff privilege.
- **Request Revision** (`#reqRev`/`#revGo`): shown to both roles unconditionally, but in the prototype's own script it only posts a comment — it never sets `exception` on the underlying record. Every `changes_requested`/`rejected` value in the prototype only ever appears in its static seed data; there is no runtime path anywhere in the script that produces one. Whatever puts a creative into an exception state is not demonstrated by the prototype at all — it's outside what can be read off it, not merely unbuilt here.
- **Unpublish** (`#unpubBtn`): published → approved, staff-only (hidden from client mode), requires typing a reason — logged only as a toast message in the prototype, not persisted anywhere structurally.
- **Revoking a stale approval** (`revokeApproval`): automatic, not a button — approved/scheduled → Client Review, fired when copy changes after sign-off or a suggested edit is accepted. The prototype's own comment states the reasoning plainly: *"Signing off then changing the work silently would leave an approval nobody gave."* A real backward transition, but a side effect of an edit, not a direct user action.

**What this schema supports today:**

- *Legal transitions per constraint*: `creatives_stage_range` only checks `stage between 1 and 8` — no ordering is enforced at all; jumping from 1 straight to 8 is not blocked by any constraint. `creatives_exception_stage` requires `exception is null or stage between 1 and 5` — so approving (stage 6+) must clear any exception first, matching every `delete s.exc` alongside every `stage=6`/`stage=5` write in the prototype's own script. Sequencing beyond that (must pass through Internal QC before Client Review, say) isn't a schema rule anywhere — it would need a new trigger or be enforced only in application code, and that choice is a product decision, not something derivable from what exists.
- *Who can make them, under the existing RLS pattern*: **already broader than the UI exposes, today, with nothing built.** `creatives_update`'s `USING` clause is `is_agency_staff(agency_id) OR (the client owns this creative's project)` — a real client-role session can already write to *any* column on a creative it can see, including `stage` and `exception`, via a direct API call, not just the columns a future approve/reject UI would touch. This isn't a gap a stage-transition feature would introduce; it already exists, inherited by anything built on top of a plain `.update()` the way every other mutation in this app is written (`useUpdateBrief`, `useSaveSlideText`, `useToggleCommentResolved` — all plain table writes, no RPC, matching the app's own established convention). Matches the prototype's intent that both roles can approve — but means nothing currently stops a client from also rewriting a creative's `name` or `concept` through that same door. Whether stage/exception writes should go through a narrower RPC instead (this schema already has that pattern for the guest path — `get_shared_review`/`submit_shared_approval`/`submit_shared_comment`, all `SECURITY DEFINER`) rather than a raw table write is a real architecture decision, not free — every other authenticated mutation in this app uses the plain-table-write convention, and departing from it here would be a first.
- *Backward transitions*: the prototype allows them (`revokeApproval`, `unpubBtn`) and the schema doesn't forbid them — no constraint or trigger cares about direction, only about the exception/stage-range pairing.
- *Audit*: the schema already flags this as a known gap in its own words — the comment above `creatives.approved_at` says outright: "there's no status_events audit table yet (deferred in Phase 1), so this is the record until that exists." That table doesn't exist for *any* transition, not just approval. Whether "who moved what, when" needs recording for stage/exception changes generally is a product decision (how much history matters vs. the schema's existing minimal footprint); *that* a real audit table is already the deferred, intended answer once it does is not — it's already written down.

**Plainly, schema vs. product:**

- Schema decisions already made and not in question: exception requires stage ≤ 5; approving clears exception; nothing enforces stage ordering.
- Schema decisions still open: whether *exception* writes (as opposed to the stage transition already built above) should move to a narrower RPC too, or reuse `creatives_update` now that it's staff-only; whether `approved_by_name/email` (denormalized for the guest case) is the right shape for an authenticated approval, or whether that needs a real `user_id` reference instead; whether a `status_events` table (already deferred, not newly proposed) lands now or later.
- Product decisions, not derivable from either the prototype or the schema: what actually produces `changes_requested`/`rejected` (the prototype never shows a working path to either); whether Request Revision should set an exception at all, or stay comment-only as the prototype's own script actually does; what "Send for Review" should mean as a manual action distinct from the automatic stage-3 bump on first upload; whether an Unpublish reason needs real structured storage rather than a toast.

## Silent-success writes and unmatched role gates — RESOLVED

Found while checking whether the deployed build (predating `phase9`) had any code writing to `creatives` in a way the newly-tightened `creatives_update` would now block, before pushing. It did — and the same audit, done properly, turned up more.

**Every mutation hook doing `.update()`/`.delete()`/`.upsert()` audited** for the pattern `useUpdateAgencyBranding` already guards against: no `.select()` after the write means RLS's ordinary "zero rows matched, zero rows changed, no error" response reads as success. Five hooks, six functions had it: `useUpdateBrief` and `useUpdateCreativeCx` (both reachable by a real client session, no UI gate at all — the actual regression risk), `useToggleCommentResolved` (UI already gates the button correctly; the hook itself had no defense if reached another way), and `useUpdateKnowledgeEntry`/`useDeleteKnowledgeEntry`/`useUpsertFormatDirection` (the first two reachable by a client with zero gating — `knowledge_entries`' write policies were staff-only before this session touched anything, the UI just never matched; the third not currently reachable, Settings already redirects non-staff, fixed anyway for consistency). All six now `.select().maybeSingle()` and throw when the row comes back null, matching the existing correct pattern exactly.

**Checked intent before touching anything** rather than assuming the RLS tightening was the problem: the prototype's Brief panel computes `canEdit = MODE!=="client" && !isLive()`, and the only way into edit mode — the pencil icon — only renders when `canEdit` is true. A client gets no edit affordance at all, not a disabled one. The project table's cell editing is gated the identical way (`if(cell&&MODE!=="client"){...startEdit...}`). On the app's own creative-review page, everything else was already `isStaff`-gated (Upload/Edit, New Brief, the stage-transition buttons) — `<BriefPanel>` was the one thing rendered with no wrapper at all. Conclusion: oversight, not intent, in every case. `creatives_update` staying staff-only was correct; the fix was UI gates, not a narrower policy anywhere.

**Fixed**: `BriefPanel` (concept/reference-link/approach-notes/text-on-image), `CxCell` (project-table custom fields) and `KnowledgeSection` (create/edit/remove) all now take `isStaff` and render read-only/hidden for a client session — disabled inputs and no Save button for `BriefPanel`, disabled inputs and no "+ Add column" for the project table, no "+ Add note"/Edit/Remove for Knowledge. `ListEditor` and `CxCell` both gained a `readOnly` prop to support this without duplicating either component. Verified empirically against real staff and client sessions (client: every control disabled or absent; staff: everything exactly as before, no change to the existing experience) before pushing.

## New Brief — RESOLVED, Copy Options still scoped out of v1

**Built**: `components/project/NewBriefModal.tsx`, entry point on the project view (`+ New Brief`, staff-only via `useIsStaff`), against the prototype's `#briefScrim`/`openBriefModal`/`bwSave` (New Brief creates a creative; separately, `renderBrief`/`saveBrief` edit an existing one — the app's `BriefPanel.tsx` already corresponds to the latter). This is the first code path in the app that creates a `creatives` row — verified empirically before any UI was written (agency_id derives correctly from the `creatives_set_agency_id` trigger with none set in the payload, stage defaults to 1, a position computed from the project's current max lands where expected, and a real client-role session is rejected outright by RLS). Content Type/Format is a real cascade over `lib/formats.ts`'s catalog, storing the key. Scheduled/continuous fields are conditionally required client-side (Publish Date, Destination) with a field-level error before submit, so the schema's `check_creative_delivery_fields` trigger — confirmed by the same empirical pass to reject a missing `scheduled_at`/`destination` outright — is a backstop, not the first thing a user meets.

Below is the original audit this was built against. Ten of the thirteen fields the modal captures map onto columns or proven versioning patterns that already existed (`creatives.name/concept/reference_url/approach_notes/lead_user_id/scheduled_at/destination/due_on/format`, `copy_versions.slide_text`, `creatives.cx`). **Copy Options (`bwCopies`, "+ Add Option") did not**, and remains the one field that needs an actual decision, not a schema change derivable from what's there — New Brief ships with a single caption into `copy_versions.fields.caption` instead (via the same insert `useSaveSlideText`/`useSaveCopyFields` already use), and no "options" concept.

The prototype's own comment calls it out as distinct from Text on Image: both "create a copy version," but Copy Options is a *list of candidate captions* offered at brief time for a copywriter to draft from — not the final content of any one version. `copy_versions.fields` (jsonb: caption/headline/cta/subject_line/preview_text/alt_text) models the opposite shape: **one version's settled content**, confirmed by how `useSaveSlideText` already uses the table — every edit inserts a new row that carries the *existing* `fields` forward untouched, changing only what that edit was for. There's no column or table anywhere for "here are three options, pick one."

Open product questions this needs answered, not derived:

- **Do options persist after one is picked?** Does choosing a caption promote it into `copy_versions.fields.caption` and the rest simply vanish, or do all candidates stay on record against the creative/version?
- **Who chooses?** The brief-writer proposes them — does the copywriter pick, does a client ever see the options, or is picking itself a staff-only action regardless of who briefed it?
- **Are rejected options kept?** If they're discarded, "Copy Options" is really just brief-writer scratch space with no lasting data shape at all — closer to a text field than a first-class list. If they're kept, that's a real new column or table, and a decision about who can read it later (comment visibility's private/public split doesn't obviously apply, but it's the closest precedent in this schema).

Building Copy Options without answering these would have meant guessing at a data shape for a concept the prototype itself doesn't fully commit to — left for a later pass once the questions above have real answers.

## `format_directions` has no delete policy at all

Found while testing New Brief's format catalog (`lib/formats.ts`) against `Settings → Knowledge`: `format_directions` has `_select`/`_insert`/`_update` RLS policies (`supabase/seed.sql`) but no `_delete` policy whatsoever — not staff-only, not admin-only, just absent. Under RLS's default-deny model that means **nobody can remove a format direction through the app, staff or admin**, once one exists. Confirmed by reading the policy list, not assumed.

This doesn't look like a deliberate scoping decision — every other place in this schema that withholds a capability says so directly (e.g. `agency_settings`'s comment explicitly says "write is admin-only"; the memberships/clients tables spell out who can do what for every operation). `format_directions` has no such comment next to the missing delete policy, which reads more like an oversight than an intentional "deletion isn't a feature here" choice.

Whether it should be one: `AddFormatForm` now selects from a fixed 41-entry catalog rather than free text, which makes mis-adding an entry (wrong format, added twice by mistake) more likely to actually happen in practice, not less — the whole catalog is one click away in a dropdown. Not being able to remove one afterward, with no workaround short of a direct database edit, looks like a real gap rather than a boundary anyone decided on purpose. Recommend adding a delete policy (staff or admin-only, matching `_update`'s reach) as a small follow-up — not done here, since this pass's job was to note the gap, not decide it.

## Primary nav — three icons led to a dead 404 — RESOLVED

`NavRail.tsx`'s `NAV_ITEMS` used to link to `/calendar`, `/analytics` and `/visibility` unconditionally, for every signed-in user, all the time, none of those routes existing anywhere under `app/`. - **Same narrower approximation of "inside a client" that `Knowledge` already has**: gated on the URL literally starting with `/clients/[id]`, not on "is this creative/project's client the one I'm in" — so the icons (like `Knowledge`) disappear again on `/projects/[id]` and `/creatives/[id]`, even though those pages belong to a client too. Extending that would need `NavRail` to know a project's or creative's `client_id`, which it doesn't fetch today; out of scope for this fix, consistent with the choice already made for `Knowledge`.

## Settings and Visibility ignored client role — RESOLVED

Found during a client-view audit, empirically: logged a real client-role session into the running app (not `previewMode` — an actual `memberships.client_id`-scoped user) and walked every built screen. `NavRail.tsx` rendered Settings unconditionally for every signed-in user, and rendered Visibility for anyone inside a `/clients/[id]` route regardless of role — both purely route-pattern gates, no permission check at all. None of the four `/settings/*` pages checked role either, so a client typing the URL directly got the real, populated agency-branding form and (until the fix below) a broken team page — full staff configuration surface, reachable and partly interactive.

The prototype's `syncRail()` treats both as real role boundaries, not reachability: `$("#navSet").style.display = client ? "none" : "grid"` hides Settings from client mode unconditionally, and `$("#navVis").style.display = (!client&&inClient)?"grid":"none"` shows Visibility only to staff — it's the screen where staff configure what a client is *allowed* to see, so showing it to the client themselves defeats the point.

**Fixed** with two layers, both keyed on real membership via a new `useIsStaff()` hook (`useMyAgency()` + `useMyMembership()`, the same pattern `CommentsPanel` already used — deliberately not `previewMode`, which doesn't restrict anything real):

- `NavRail.tsx` hides both Settings and Visibility unless `isStaff` (and hides them while that's still resolving — fails closed, never shows staff-only nav to a session not yet confirmed staff).
- `app/(app)/settings/layout.tsx` — the one layout wrapping all four `/settings/*` routes — redirects a non-staff session to `/dashboard` before rendering any tab content, so a direct URL is closed the same way the nav link already was. No dedicated "forbidden" page exists in this app yet, and a client landing on their own dashboard is a real, useful place to end up rather than a dead end.

Verified empirically both directions: a real client-role session sees neither nav item and gets redirected off every settings page (`tests/e2e/nav-rail.spec.ts`, `tests/e2e/settings.spec.ts`); a real staff session still sees and reaches all of it.

## The stage pipeline, simplified from 8 stages to 4 — and a real bug fixed for the whole agency's real data

A real bug report started this: a creative ("This is a Test Post") with both copy and artwork already saved was still showing as Concept — the user's own definition of Concept being "no copy and no creative has been written yet." Investigation (not assumed — read every RPC, constraint, and hook that touches `stage`, then confirmed against real production data via `supabase db query`) found this wasn't a display bug: **nothing in the app has ever advanced a creative's stage automatically.** A creative is created at stage 1 and stays there forever unless a staff member manually clicks the Internal Review/Client Review toggle. Stages 2 (Copy) and 3 (Design) were unreachable by any code path at all — `advance_creative_stage` jumped straight from "anything < 5" to 5, and back down to a hardcoded 4, never touching 2 or 3. Stages 7 (Scheduled) and 8 (Published) were equally unreachable — nothing anywhere set them (confirmed by repo-wide search). Only stage 6 (Approved) was ever reached, and only via a guest's shared-review-link approval.

The user asked for the plain-English list of what currently changes a stage (exactly three things: creation defaults to stage 1; the manual toggle; a guest approval — nothing reacts to content existing), then explicitly authorized simplifying the model to match reality: **Concept, Internal Review, Client Review, Approved** — collapsing the unreachable stages rather than just relabelling them, and dropping Scheduled entirely (confirmed dead, not just redundant).

**Concept → Internal Review is now automatic** — a Postgres trigger (`bump_creative_from_concept()`, firing `after insert` on both `creative_versions` and `copy_versions`) bumps a creative off stage 1 the instant either its first copy or its first artwork is saved, whichever comes first. Enforced at the database layer rather than an app-code call some hook could forget, matching this codebase's own established preference (`advance_creative_stage` already lives at this layer for the same reason). This directly encodes the user's own definition of Concept and is what actually fixes "Test Post" going forward, not just this once.

**Two follow-up decisions, confirmed with the user directly before writing any migration**: add a staff-side Approve action (today Approved was only reachable via a client/guest link, despite the app's own docs noting the prototype intended a staff "Approve on Behalf" too), and add a way to revoke one. Both landed as one change: the manual toggle grew a third segment — Internal Review / Client Review / Approved — always visible to staff now, every segment independently clickable. Clicking "Client Review" while Approved *is* the revoke path; no separate button needed.

**Migration** (`supabase/migrations/phase13_simplify_stage_pipeline.sql`, mirrored into `supabase/seed.sql`): remapped existing data first, content-aware for the exact bug this was about (a stage-1 row with a real `creative_versions`/`copy_versions` row already attached remaps to Internal Review, not blindly to the new stage 1) — checked against real data before writing it: 12 real creatives, "This is a Test Post" confirmed among them at stage 1 with 1 artwork version and 2 copy versions. Then narrowed `creatives_stage_range` (1-4) and `creatives_exception_stage` (1-3); replaced `advance_creative_stage` with three permissive directions (`to_internal`/`to_review`/`to_approved`, any from any stage, raising only on a genuine no-op) — the new `to_approved` branch mirrors `submit_shared_approval`'s attribution shape (`approved_at`/`approved_by_name`/`approved_by_email`) but sources the name/email from the staff caller's own `users` row instead of a guest-supplied name; the other two clear those same three columns, so a revoked approval doesn't leave a stale "approved by X" record sitting against a non-approved stage. Also updated `shared_link_allowed_creative_ids` (`stage >= 3`) and, as a drive-by correctness fix while already touching it, made `submit_shared_approval` clear `exception` on approval (it didn't before — harmless today since nothing sets `exception` anywhere in the app, but the newly-narrowed exception/stage constraint would otherwise reject an approval on any creative that ever did have one).
