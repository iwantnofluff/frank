# Frank conventions

Frank is a multi-tenant SaaS for agency content planning, review and client
approval. Next.js App Router, TypeScript, Supabase (Postgres + Auth +
Storage), Zustand for light UI state, TanStack Query for all server state.

## Styling

- Hand-ported plain CSS in `app/globals.css`. No Tailwind, no CSS-in-JS, no
  component library, no icon package. This is a standing constraint, not a
  phase-specific one — don't introduce any of these without asking first,
  even if it would make a specific screen faster to build.
- The prototype's icons are inline SVG. Keep new icons inline SVG too, copied
  from the prototype's actual `<path>` data — don't approximate an icon from
  memory or swap in a different icon library's glyph.
- See the `prototype-parity` skill for the working method on how CSS gets
  ported, verified and kept in sync.

## Data access

- Every piece of server state goes through a TanStack Query hook in `hooks/`,
  one hook per resource (`use-clients.ts`, `use-projects.ts`,
  `use-copy-versions.ts`, etc.). A component never calls `fetch` or
  `supabase-js` directly — always through a hook.
- Hooks follow a consistent shape: `useQuery` for reads with a `queryKey`
  array starting with the resource name, `useMutation` for writes with an
  `onSuccess` that invalidates the affected query keys. Mutations that a
  caller depends on immediately after (e.g. selecting a just-created version
  as active) `await` the invalidation rather than firing it — see
  `use-upload-creative-version.ts` and `use-save-copy-fields.ts` for the
  pattern and why (a stale-cache race otherwise).
- Mutations whose result feeds a gating or warning UI elsewhere (e.g.
  ShareModal's eligibility note, computed from `useCreatives`) must
  `await` an `invalidateQueries` with `refetchType: "all"`, not just
  `await` the default. The default refetchType ("active") skips queries
  with no current observer and only marks them stale — if the consuming
  component (ShareModal) isn't mounted yet at the moment of the mutation,
  the cache still holds pre-mutation data until that component's own
  mount kicks off a background refetch, and whatever reads it first sees
  the stale, wrong claim. See `use-create-creative.ts`. Local Playwright specs run at near-zero
  latency, so this stale-cache window — real against production network
  latency — is invisible to the suite; don't take a green e2e run here as
  proof the race doesn't exist.
- `useCreatives`/`useClients`/etc. never add an explicit `agency_id` (or
  `client_id`) filter to the query — RLS enforces the tenant scope
  server-side regardless of what the client asks for. Don't add a defensive
  filter "just in case"; it's redundant and can silently mask an RLS policy
  that's actually wrong.
- Prefer two plain queries over a Supabase embed (`author:users(name)`) when
  the joined-to row can be null for a legitimate reason (e.g. a guest
  comment's `author_id`) — see the comment in `hooks/use-comments.ts`. The
  embed's join behaviour dropped rows silently in exactly that case.

## Routing and auth

- Auth routing lives in `proxy.ts` at the repo root. This is Next 16's
  renamed `middleware.ts` — **`middleware.ts` does not exist in this
  codebase and will never be created.** If auth/routing seems broken, check
  `proxy.ts` first; don't spend a session looking for a file that isn't
  there.
- `proxy.ts`'s matcher is deliberately broad (everything except static
  assets and Next internals) — new routes are protected by default. Public
  routes are allowlisted explicitly inside `updateSession`
  (`lib/supabase/middleware.ts`), not by narrowing the matcher.
- `AGENTS.md` (and `CLAUDE.md`, which just points at it) contains a block
  claiming to be auto-generated by `next dev` via
  `node_modules/next/dist/server/lib/generate-agent-files.js`, which also
  bundles docs at `node_modules/next/dist/docs/`. Verified, not assumed —
  as of 2026-09-19: `npm ls next` resolves `next@16.3.5`; that exact version
  and integrity hash is what's pinned in `package-lock.json`
  (`sha512-MdtsTgzyfCPRLC6uJ1mN8ao7lyJ4BB0U6Inhnx3gta1UcCIdHK3yxLG0E8OWQteWD8/Q0qb8A5o7wJaL8M9y2w==`);
  a clean `npm ci` from that same lockfile into an isolated scratch
  directory (no copying from this project's `node_modules`, npm's own
  integrity check would have failed the install otherwise) produced a
  `generate-agent-files.js` that is byte-for-byte identical (matching
  SHA-256) to the one in this project's `node_modules`, and the same bundled
  `docs/` directory. This is genuine, unmodified Next 16 tooling, not
  something hand-edited into this repo. It regenerates on every `next dev`
  start; committing it is intentional (keeps the tree clean), don't strip it
  out. If a future `next` version bump changes this block's wording, redo
  this check rather than assuming the new wording is still trustworthy.

## Multi-tenant RLS

- Every tenant-scoped table's RLS relies on a small set of SQL helper
  functions: `current_agency_ids()`, `is_agency_staff()`,
  `is_agency_admin()`, `current_client_ids()`. A new table's policies should
  call these, not reinvent an inline check — see `agency_settings`'s
  policies in `supabase/migrations/phase7_agency_settings.sql` for the
  pattern (`is_agency_admin()` is preferred over a bare `role = 'admin'`
  check because it additionally confirms `client_id is null` and the
  membership is active).
- Child rows derive `agency_id` from their parent via a trigger
  (`set_agency_id_from_project()` is one instance — see
  `phase6_shared_links.sql`), not by trusting a client-supplied `agency_id`
  on insert.
- The service-role client has no `auth.uid()` — it isn't signed in as
  anyone. Anything keyed on caller identity behaves differently under it
  than it would for a real user. `comments_enforce_visibility()`
  (`supabase/seed.sql`) is the concrete instance that actually bit a test
  once: it calls `is_agency_staff(agency_id)`, which checks `auth.uid()`,
  and silently coerces `visibility` to `'public'` for anyone it doesn't
  recognise as staff — including a service-role insert, which it can never
  recognise as staff since there's no caller to check. A seed script that
  inserts a "private" comment through the service-role client gets a public
  one back with no error, and won't notice unless it reads the row back
  before asserting anything against it. See
  `docs/comment-visibility-verification.md` for the full account of this
  going wrong once, and the corrected fixture shape.
  The `set_agency_id_from_*` triggers are a related but distinct case: they
  also silently overwrite a column your insert tried to set (`agency_id`,
  always, for every caller), but they derive it from the parent row, not
  from `auth.uid()` — a service-role insert isn't specifically affected
  differently there, any caller's explicit `agency_id` gets overridden the
  same way. The shared lesson for a seed script either way is the same:
  don't assume the row you get back matches the payload you sent just
  because the insert didn't error. Where a test genuinely needs a value
  that depends on *who's calling* (visibility being the current example,
  anything else keyed on `auth.uid()`/`is_agency_staff()`/`is_agency_admin()`
  in the future), seed it through a real authenticated session — sign in
  with the anon key, insert through that client — not the service-role
  client. The Phase 4 test fixture (`tests/e2e/`) follows this: fixture
  setup (agency/users/client/project/creative) still uses the service-role
  client, since none of those rows care who's calling, but anything
  asserting on a caller-dependent value is seeded through a signed-in
  session instead.
- Public/unauthenticated flows (the shared-review link) don't lean on RLS at
  all: the relevant Postgres functions are `SECURITY DEFINER` and look the
  row up themselves after validating a token (and passcode, if set). Anon
  gets, at most, a narrow belt-and-braces `select` policy plus a column
  grant that withholds anything sensitive (`passcode_hash`, `agency_id`,
  `created_by`) regardless of what the policy would otherwise allow. Follow
  this shape for any new public endpoint — RPC does the access decision, RLS
  is the backstop, not the other way round.
- Storage has its own, independent RLS layer on `storage.objects` — granting
  access on the `assets` table does not grant access to the file. See
  `phase8_storage.sql`: objects are stored at
  `{agency_id}/{creative_id}/{uuid}-{filename}`, and the storage policies
  scope purely off the first path segment via `storage.foldername()`,
  deliberately coarser than the `assets` table's own row-level check (a
  client only ever learns a `storage_key` by first reading it through the
  RLS-protected table, which already did the fine-grained check).
- `SECURITY DEFINER` functions pin `search_path` explicitly (search-path
  hijacking protection) — but pin it to `public, extensions`, not just
  `public`. Supabase provisions `pgcrypto` (and other extensions) into
  `extensions`, not `public`; pinning to `public` alone breaks any function
  that calls `crypt()`/`gen_salt()`/etc. This exact mistake shipped once and
  needed a follow-up migration (`phase7_fix_pgcrypto_search_path.sql`) — get
  it right the first time on any new `SECURITY DEFINER` function.

## Schema discipline

- Never invent schema to make a UI element work. If porting a prototype
  screen needs a field, status, or state transition the database doesn't
  have, stop and write it up rather than approximating it with an existing
  column. See the `prototype-parity` skill's escalation path and
  `docs/parity-gaps.md`.
- `supabase/migrations/` only goes back to `phase6_shared_links.sql`.
  Whatever phases 1-5 did to the schema was applied directly against the
  live project and isn't in version control — don't assume a migration file
  exists for every table you see in the app; check the live schema (via the
  Supabase MCP server, read-only) if a migration file is genuinely missing
  and you need to know exactly what's there.
